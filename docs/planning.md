# マイルストーン設計とタスクの見積もり

マイルストーンを設計・再設計するときのルールです。人間も AI エージェントもこの文書に従います。

> 前提: 開発の見積もりは外れる。
> 当てにいくのではなく、着手から merge までの実績 (スループット) を計測し、見積もりを直し続ける。

計画の実体は GitHub に置きます。このリポジトリには日程表を持ちません (二重管理になるため)。

| 何を                    | どこに                                                                       |
| ----------------------- | ---------------------------------------------------------------------------- |
| マイルストーンと期日    | GitHub Milestones                                                            |
| Issue の大きさ          | [Project #34](https://github.com/orgs/NUTFes/projects/34) の `Size`          |
| Issue の着手日 / 完了日 | Project #34 の `Start` / `Target`                                            |
| 依存関係                | Issue の依存関係 (`Blocked by` / `Blocking`)。Epic と子は親子 (Sub-issues) |

## 見積もりの単位: 枠

Issue 1 件を 1 枠 (1〜1.5h) として見積もります。1 枠の内訳は次のとおりです。

| #   | 工程                                                 | 目安      |
| --- | ---------------------------------------------------- | --------- |
| 1   | Issue 本文から仕様を確認し、壁打ちで詳細設計を詰める | 20min     |
| 2   | 初回実装                                             | 15min     |
| 3   | PR の AI セルフレビューと、それを踏まえた修正        | 10min     |
| 4   | 人間によるセルフレビュー                             | 15min     |
| 5   | セルフレビューと修正実装のサイクル                   | 15〜30min |
| 6   | マージとデプロイ                                     | -         |

1 枠に収まらない Issue は、Project の `Size` で枠数を決めます。

| Size          | 枠数 | 扱い                                        |
| ------------- | ---- | ------------------------------------------- |
| Tiny / Small  | 1    | そのまま着手する                            |
| Medium        | 2    | そのまま着手してよい。分割できるなら分割する |
| Large 以上    | 3〜  | 着手前に 1〜2 枠の子 Issue へ分割する       |

- Epic は枠に数えません (子 Issue の合計がその Epic の枠数)
- 調査・合意形成の Issue は、作業時間ではなく相手の返事待ちで期日が決まります。枠は 1 のまま、`Target` だけ後ろに置きます

## マイルストーンの組み方

- 1 日の稼働は 3h 程度、**1 日に着手するのは最大 3 枠**。稼働日は平日のみ
- マイルストーンの実装日数 = 枠数 ÷ 3 の切り上げ。依存関係で同じ日に並べられない場合は日数を増やす
- 各マイルストーンの最終日は **予備日 兼 振り返り** とし、枠を置かない
  - 振り返りでは `throughput` を見て、次のマイルストーン以降の日程を引き直す
- 日程を決めたら、Milestone の期日と、各 Issue の `Start` / `Target` を更新する
- 依存関係のある Issue は、先行の `Target` より前に `Start` を置かない

設定後は必ず次のコマンドで確認します。1 日の枠数の超過、依存の順序の逆転、期日の超過が警告として出ます。

```bash
node scripts/plan.mjs status
```

## スループットの計測

Issue ごとに、**PR の最初のコミットから merge まで** の経過時間を計測します。休憩も工数に含めるので、除外はしません。

設計 (工程 1) にはコミットが残らないため、着手時に空のコミットを打って開始時刻を記録します。次のコマンドが、ブランチ作成・着手コミット・push・Draft PR 作成 (`resolve #<issue番号>` 入り) までを行います。

```bash
scripts/start-issue.sh <issue番号> [ブランチ名]
```

- **仕様確認を始める前に実行する**。実装を始めてから打つと、設計の時間が計測から漏れる
- 計測は PR 単位。担当者以外 (レビュワーの軽微な修正など) が同じ PR にコミットしても、そのまま含める
- Issue への assign は担当の割り振りに使うもので、計測には使わない

```bash
node scripts/plan.mjs throughput
```

- 主な指標は **稼働日あたりの消化枠数**。計画値は 3 枠/日
- Issue ごとの所要時間は、1 枠 = 1〜1.5h の見積もりと比べる
- 出力の「実績ペースで あと N 稼働日」が、残りの日程を引き直すときの基準
- 着手コミットなしで始めた PR は `※着手コミットなし` と表示される (所要時間が短く出る)

## 再設計するとき

次のいずれかに当てはまったら、マイルストーンを組み直します。

- マイルストーンの振り返り (予備日)
- 実績が計画から 1 日以上ずれた
- 新しい Issue を追加した、または優先順位を変えた
- 先行 Issue の結論で、後続の前提が変わった (例: #9 の結論で Epic C の設計が変わる)

手順:

1. 新しい Issue は起票時に、Project への追加・`Size`・親 Epic・依存関係 (`Blocked by`) を設定する
2. 影響範囲を確認する。対象 Issue の先行と後続を、依存関係をたどって表示します

   ```bash
   node scripts/plan.mjs impact <issue番号>
   ```

3. `throughput` の実績ペースで、影響を受けるマイルストーンの日数を計算し直す
4. Milestone の期日と、影響を受ける Issue の `Start` / `Target` を更新する
5. `status` で警告が出ないことを確認する

優先順位の変更はマイルストーンをまたぐので、Issue 単体ではなく Project 全体 (`status` の出力) を見て判断します。
期日を動かす、Issue を別のマイルストーンへ移す、スコープを削る、といった判断は人間が行います。エージェントは影響範囲と選択肢を示すところまでです。

### 依存関係の登録

GitHub の Issue 画面の「Relationships」から設定できます。CLI からは次のとおりです。

```bash
# #12 は #13 が終わるまで着手できない、を登録する
gh api graphql \
  -f query='mutation($i:ID!,$b:ID!){addBlockedBy(input:{issueId:$i,blockingIssueId:$b}){issue{number}}}' \
  -f i="$(gh issue view 12 --json id --jq .id)" \
  -f b="$(gh issue view 13 --json id --jq .id)"
```

Issue 本文の「先行」「前提」に書くだけでは `impact` に反映されません。必ず依存関係として登録します。
