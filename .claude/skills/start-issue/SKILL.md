# Issue に着手して実装計画を決める

対象の Issue: $ARGUMENTS (指定がなければユーザーに番号を確認する)

設計担当のスキルです。担当の割り当てと全体の流れは `AGENTS.md` の「開発フローと責務分担」にあります。
このスキルでは実装しません。成果物は Issue 本文の実装計画で、実装は `implement` スキル (実装担当) が行います。

工程と時間の目安は `docs/planning.md` の「見積もりの単位: 枠」にあります。1 枠 (1〜1.5h) に収まらないと分かった時点で、黙って続けずユーザーに伝えてください。

## 1. 着手して、壁打ちを始められる状態にする

何よりも先に、次の手順で着手します (着手コミットの時刻がスループット計測の開始時刻になるため)。Issue 本文や関連コードは、スクリプトを実行するまで読みません。

1. Issue のタイトルだけを取得します (`gh issue view <issue番号> --json title --jq .title`)
2. タイトルから `{内容}` を決めます (英小文字・数字のハイフン区切り、2〜4 語。ユーザーには尋ねません)
3. 次のコマンドを実行します

```bash
.claude/skills/start-issue/start.sh <issue番号> <内容>
```

これだけで壁打ちの手前まで終わります。

1. worktree (`.claude/worktrees/issue-<issue番号>`) とブランチの作成
2. 空の着手コミット → push → Draft PR の作成 (`resolve #<issue番号>` 入り、prefix に応じたラベル付与)
3. 環境構築 (`.env.local` のコピー、`npm ci`)
4. Issue 本文と、依存関係から見た影響範囲 (先行 / 後続) の表示

最後に `pr: <URL>` と `worktree: <パス>` が出力されます。続けて、そのパスへ作業場所を移します。以降の作業はすべてこの worktree の中で行います。

- Claude Code: `EnterWorktree` に `path` を渡す
- それ以外: そのパスへ `cd` する

すでに同じ Issue の worktree がある場合、スクリプトは失敗します。作り直さず、既存の worktree に入って続きから進めてください。

## 2. 壁打ちで詳細設計を詰める

- 1 で表示された Issue 本文をもとに、関連するコードを確認する
- 影響範囲に未完了の先行があれば、最初にユーザーへ伝える
- 決まっていない点をユーザーに質問して詰める。コードを読めば分かることは質問しない

## 3. 実装計画を Issue に書く

実装担当は壁打ちの会話を見ていません。Issue 本文だけで実装できるように書きます。
Issue 本文の「考えられる開発内容」を、決まった内容の「実装計画」に置き換えます (起票時の案は Issue の編集履歴に残ります)。

```bash
gh issue view <issue番号> --json body --jq .body > <ファイル>   # これを編集する
gh issue edit <issue番号> --body-file <ファイル>
```

```markdown
# 開発目的
<!-- 壁打ちで変わった点があれば直す。何がどうなれば完了かが分かるようにする -->

# 実装計画

## 変更範囲
<!-- 変更するファイルと、それぞれで行うこと。新規ファイルも書く -->
- `path/to/file.tsx`: ...

## やらないこと
<!-- 壁打ちで範囲外と決めたこと。ついでに直したくなりそうな箇所は明記する -->

## 受け入れ条件
<!-- レビューで確認できる形で書く。確認コマンドや操作手順を含める -->
- [ ] ...

# 考えられる開発時間
# 備考
<!-- 既存の内容は残す。設計上の判断とその理由を追記する -->
```

- 「変更範囲」に挙げていないファイルは、実装担当が変更できない。必要なファイルは漏らさず書く
- PR 本文の「概要」には、実装計画が Issue にあることだけを書く (同じ内容を 2 箇所に書かない)

## 4. 実装担当へ引き継ぐ

自分では実装に進みません。`handoff` スキルで実装担当に依頼します。

- 依頼文: `implement スキルで #<issue番号> を実装してください。`
- 実装担当の作業が終わったら、続けて `self-review` スキルでレビューする

## 計画を直すとき

実装やレビューの途中で計画の不足が見つかると、設計担当に戻ってきます。
ユーザーと相談して Issue の実装計画を更新し、変更点を PR にコメントしてから、`handoff` スキルで実装担当へ依頼し直します。
