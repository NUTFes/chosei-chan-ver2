# PR を実装計画と照らしてレビューする

対象の Issue: $ARGUMENTS (指定がなければ、今いる worktree のブランチの PR を対象にする)

レビュー担当のスキルです。担当の割り当てと全体の流れは `AGENTS.md` の「開発フローと責務分担」にあります。
このスキルではコードを直しません。成果物は PR への指摘コメントで、修正は `implement` スキル (実装担当) が行います。

## 1. 状況を確認する

作業場所は Issue の worktree (`.claude/worktrees/issue-<issue番号>`) です。別の場所にいる場合は移動します。

```bash
git pull
gh pr view --json number,url,body --jq '.url, .body'
gh pr view --comments
gh pr diff
```

2 回目以降のレビューでは、前回の指摘と実装報告を読み、対応済みかどうかから確認します。

## 2. レビューする

実装計画を基準に、次の順で見ます。

1. **範囲**: 「変更範囲」にないファイルが変更されていないか。「やらないこと」に手を付けていないか
2. **受け入れ条件**: 条件を 1 つずつ自分で確認する。実装報告の「確認できた」を鵜呑みにしない
3. **正しさ**: バグ、考慮漏れ、既存の挙動を壊していないか
4. **確認コマンド**: 次が通るか

   ```bash
   npm run lint
   npm run build
   ```

計画そのものの誤りや不足に気づいた場合は、実装への指摘にせず、設計担当へ戻す事項として分けて書きます。

## 3. 結果を PR にコメントする

`gh pr comment <PR番号> --body-file <ファイル>` で、次の形でコメントします。

```markdown
## AI セルフレビュー (N 回目)

### 指摘
1. [必須] `path/to/file.tsx:42` 何が問題か。どう直すか
2. [任意] ...

### 受け入れ条件
- [x] 確認できた条件
- [ ] 満たしていない条件 (指摘 1)

### 計画の見直しが必要な点
なし、または内容
```

- 指摘には番号、`[必須]` か `[任意]`、ファイルと行、直し方を書く。実装担当が指摘だけを読んで直せるようにする
- `[必須]` は、受け入れ条件を満たさない、バグがある、範囲を逸脱している、のいずれか。好みの問題は `[任意]` にするか書かない

## 4. 次へ引き継ぐ

- **`[必須]` の指摘がある**: ユーザーに、実装担当のエージェントで `implement` スキルを使って修正するよう伝える
- **計画の見直しが必要**: ユーザーに、設計担当 (`start-issue` スキルの「計画を直すとき」) へ戻すよう伝える
- **`[必須]` の指摘がない**: PR 本文の「テスト項目」を人間が確認する手順で埋め、Draft を外して、ユーザーにレビューを依頼する

  ```bash
  gh pr ready
  ```

人間のレビューで指摘が出た場合も、修正は `implement` スキルで行い、修正後にこのスキルでもう一度レビューします。
マージはユーザーが行います。マージ後は worktree を片付けます。

```bash
git worktree remove .claude/worktrees/issue-<issue番号>
```
