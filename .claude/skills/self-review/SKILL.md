# PR を実装計画と照らしてレビューする

対象の Issue: $ARGUMENTS (指定がなければ、今いる worktree のブランチの PR が閉じる Issue を対象にする)

レビュー担当のスキルです。担当の割り当てと全体の流れは `AGENTS.md` の「開発フローと責務分担」にあります。
このスキルではコードを直しません。成果物は PR への指摘コメントで、修正は `implement` スキル (実装担当) が行います。

## 1. 状況を確認する

作業場所は Issue の worktree (`.claude/worktrees/issue-<issue番号>`) です。別の場所にいる場合は移動します。

```bash
git pull
gh pr view --json number,url,closingIssuesReferences   # PR と、対応する Issue 番号
gh issue view <issue番号>                               # 実装計画
gh pr view --comments                                   # 実装報告と前回までの指摘
gh pr diff
```

2 回目以降のレビューでは、前回の指摘が実装報告のとおり対応されているかから確認します。

## 2. レビューする

実装計画を基準に、次の順で見ます。

1. **範囲**: 「変更範囲」にないファイルが変更されていないか。「やらないこと」に手を付けていないか
2. **受け入れ条件**: 条件を 1 つずつ自分で確認する。実装報告の「確認できた」を鵜呑みにしない
3. **正しさ**: バグ、考慮漏れ、既存の挙動を壊していないか
4. **確認コマンド**: 次が通るか

   ```bash
   npm run lint
   npm run build
   ```

計画そのものの誤りや不足に気づいた場合は、実装への指摘にせず、設計担当へ戻す事項として分けて書きます。

## 3. 指摘のラベル

| ラベル     | 意味                                                             | 実装担当の対応             |
| ---------- | ---------------------------------------------------------------- | -------------------------- |
| `must`     | 直さないとマージできない (受け入れ条件の未達、バグ、範囲の逸脱)  | 必ず直す                   |
| `should`   | 直すべき (保守性や一貫性の問題。放置すると後で困る)              | 直す。見送るなら理由を返す |
| `want`     | できれば直したい (小さな改善)                                    | 小さく済むなら直す         |
| `imo`      | 意見。別のやり方の提案や好み                                     | 直さない。人間が判断する   |
| `question` | 意図が読み取れない箇所の確認                                     | コードは変えず回答する     |

迷ったら低いほうのラベルにします。好みの問題を `must` や `should` にしません。

## 4. 結果を PR にコメントする

`gh pr comment <PR番号> --body-file <ファイル>` で、次の形でコメントします。

````markdown
## AI セルフレビュー (N 回目)

must 1 件 / should 1 件 / question 1 件。修正が必要です。

### 1. [must] 逆方向にドラッグすると選択範囲が空になる
- 場所: `src/components/screen/ScheduleInput/ScheduleInput.tsx:88-91`
- 問題: anchor より前のセルへドラッグすると `start > end` になり、範囲が 0 件になる
- 修正: 範囲計算の前に `start` と `end` を `Math.min` / `Math.max` で正規化する
- 確認: 14:00 から 12:00 へドラッグして、12:00〜14:00 が選択されること

### 2. [should] ...

### 3. [question] `selectedTimes` をコピーせずに sort しているのは意図どおりか
- 場所: `...:54`
- 質問: ...

### 受け入れ条件
- [x] 確認できた条件
- [ ] 満たしていない条件 (指摘 1)

### 計画の見直しが必要な点
なし
````

読み手は主に実装担当のエージェントです。指摘だけを読んで直せるように書きます。

- 見出しに通し番号・ラベル・一言の要約を書く (人間が見出しだけ拾っても状況が分かるようにする)
- 「場所」はファイルと行。「問題」は何が起きるかと再現条件。「修正」は具体的な直し方。「確認」は直ったことの確かめ方
- 1 つの指摘に 1 つの問題だけを書く。複数箇所にまたがる同じ問題は、場所を並べて 1 つにまとめる
- 冒頭の 1 行に、ラベルごとの件数と結論を書く
- 褒め言葉や総評は書かない

## 5. 次へ進める

- **`must` か `should` の指摘、または `question` がある**: `handoff` スキルで実装担当に修正を依頼する。依頼文: `implement スキルで #<issue番号> のレビュー指摘 (AI セルフレビュー N 回目) に対応してください。` 終わったら、このスキルでもう一度レビューする
- **計画の見直しが必要**: 実装担当には依頼せず、ユーザーに伝えて設計 (`start-issue` スキルの「計画を直すとき」) へ戻す
- **残っているのが `want` と `imo` だけ**: PR 本文の「テスト項目」を人間が確認する手順で埋め、Draft を外して、ユーザーにレビューを依頼する

  ```bash
  gh pr ready
  ```

レビューと修正の往復が 3 回を超えたら、続けずにユーザーへ状況を伝えて判断を仰ぎます。

人間のレビューで指摘が出た場合も、修正は `handoff` スキルで実装担当に依頼し、修正後にこのスキルでもう一度レビューします。
マージはユーザーが行います。マージ後は worktree を片付けます。

```bash
git worktree remove .claude/worktrees/issue-<issue番号>
```
