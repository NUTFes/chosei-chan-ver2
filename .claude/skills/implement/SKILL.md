# 実装計画どおりに実装する

対象の Issue: $ARGUMENTS (指定がなければ、今いる worktree のブランチの PR が閉じる Issue を対象にする)

実装担当のスキルです。担当の割り当てと全体の流れは `AGENTS.md` の「開発フローと責務分担」にあります。
何を作るかは設計担当が決め、Issue 本文の「実装計画」に書いてあります。このスキルは、その計画を範囲どおりに実装します。

## 1. 状況を確認する

作業場所は Issue の worktree (`.claude/worktrees/issue-<issue番号>`) です。別の場所にいる場合は移動します。

```bash
git pull
gh pr view --json number,url,closingIssuesReferences   # PR と、対応する Issue 番号
gh issue view <issue番号>                               # 実装計画
gh pr view --comments                                   # 実装報告とレビュー指摘
```

- Issue 本文に「実装計画」がなければ、実装を始めない。設計担当 (`start-issue` スキル) が先だと伝えて終わる
- 未対応のレビュー指摘 (`## AI セルフレビュー` のコメント、人間のレビューコメント) があれば **修正** を、なければ **初回実装** を行う

## 2. 守ること

- 変更してよいのは、実装計画の「変更範囲」に挙がっているファイルだけ
- 「やらないこと」に書かれた内容には手を付けない。気づいた改善点は実装せず、実装報告で伝える
- 計画どおりでは実装できない、範囲を広げる必要がある、と分かったら、自分の判断で進めず止まる。理由と必要な変更を PR にコメントし、設計担当へ戻す必要があると伝える

## 3. レビュー指摘への対応 (修正のとき)

指摘のラベルごとに対応を決めます。指摘にない書き換えは混ぜません。

| ラベル     | 対応                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| `must`     | 必ず直す                                                               |
| `should`   | 直す。直さない場合は理由を実装報告に書く                               |
| `want`     | 変更範囲の中で小さく直せるなら直す。そうでなければ見送り、理由を書く   |
| `imo`      | 直さない (レビュー担当の意見。採用するかは人間が決める)                |
| `question` | コードは変えず、実装報告で回答する                                     |

## 4. 実装して確認する

- コミットは意味のある単位で分ける
- push の前に次を通す

  ```bash
  npm run lint
  npm run build
  ```

- 「受け入れ条件」を 1 つずつ確認する。確認できなかった条件は、その旨を実装報告に書く

## 5. push して報告する

```bash
git push
```

PR に次の形でコメントします (`gh pr comment <PR番号> --body-file <ファイル>`)。

```markdown
## 実装報告 (N 回目)

- 実装した内容: ...
- 受け入れ条件: 確認できたもの / 確認できなかったものと理由
- 計画と違う点: なし、または内容と理由

<!-- 修正のときは、指摘の番号ごとに書く -->
- 指摘 1 [must]: 対応した (コミット abc1234)
- 指摘 2 [want]: 見送った。理由: ...
- 指摘 3 [question]: 回答: ...
```

Draft を外したりマージしたりはしません。報告をコメントしたら終わりです。続きはレビュー担当が `self-review` スキルで行います。
