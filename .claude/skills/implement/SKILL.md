# 実装計画どおりに実装する

対象の Issue: $ARGUMENTS (指定がなければ、今いる worktree のブランチの PR を対象にする)

実装担当のスキルです。担当の割り当てと全体の流れは `AGENTS.md` の「開発フローと責務分担」にあります。
何を作るかは設計担当が決め、PR 本文の実装計画に書いてあります。このスキルは、その計画を範囲どおりに実装します。

## 1. 状況を確認する

作業場所は Issue の worktree (`.claude/worktrees/issue-<issue番号>`) です。別の場所にいる場合は移動します。

```bash
git pull
gh pr view --json number,url,body,isDraft --jq '.url, .body'
gh pr view --comments
```

- PR 本文に「実装計画」がなければ、実装を始めない。設計担当 (`start-issue` スキル) が先だとユーザーに伝えて終わる
- 未対応のレビュー指摘 (`## AI セルフレビュー` のコメント、人間のレビューコメント) があれば **修正** を、なければ **初回実装** を行う

## 2. 守ること

- 変更してよいのは、実装計画の「変更範囲」に挙がっているファイルだけ
- 「やらないこと」に書かれた内容には手を付けない。気づいた改善点は実装せず、PR へのコメントで伝える
- 修正のときは、指摘された箇所だけを直す。指摘にない書き換えを混ぜない
- 計画どおりでは実装できない、範囲を広げる必要がある、と分かったら、自分の判断で進めず止まる。理由と必要な変更を PR にコメントし、設計担当へ戻すようユーザーに伝える

## 3. 実装して確認する

- コミットは意味のある単位で分ける
- push の前に次を通す

  ```bash
  npm run lint
  npm run build
  ```

- 「受け入れ条件」を 1 つずつ確認する。確認できなかった条件は、その旨を報告に書く

## 4. push して報告する

```bash
git push
```

PR に次の形でコメントします (`gh pr comment <PR番号> --body-file <ファイル>`)。

```markdown
## 実装報告

- 実装した内容: ...
- 受け入れ条件: 確認できたもの / 確認できなかったものと理由
- 計画と違う点: なし、または内容と理由
```

修正のときは、指摘の番号ごとに「対応した」「見送った (理由)」を書きます。

## 5. レビュー担当へ引き継ぐ

Draft を外したりマージしたりはしません。ユーザーに次を伝えて終わります。

- 次の手順: 同じ worktree でレビュー担当のエージェントを起動し、`self-review` スキルで `#<issue番号>` をレビューする
